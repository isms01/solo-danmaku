# 一人ニコニコ動画（solo-danmaku）仕様書

**Version**: 0.1
**Status**: Prototype（単一HTMLファイル実装、動作検証中）
**Author**: Masa

---

## 1. 背景

### 1.1 解こうとしている問題

ニコニコ動画のコメント弾幕が持つ価値は、動画そのものではなく **「他人と同じ瞬間に反応している」という感覚** にある。しかし弾幕が成立するには一定の視聴者母数が必要で、以下のケースでは原理的に成立しない。

- 手元のローカル動画（自分で撮影した映像、家族の記録、練習動画）
- 視聴者数が集まらない動画
- 配信プラットフォームに上げられない private な映像

つまり「弾幕を見たいが、弾幕を生む群衆が存在しない」という供給不在の問題である。

### 1.2 アプローチ

視聴者の代わりに、LLM（vision モデル）に映像を見せてコメントを生成させる。単なるテキスト生成ではなく、**複数人格の群れとして生成する**ことで弾幕特有の「議論・同意・逆張りが混ざったノイズ感」を再現する。

### 1.3 副次的な目的

本プロジェクトは実用ツールであると同時に、以下の設計パターンの検証を兼ねている。

- **LLM 出力の非決定性を、決定的なレンダリング層で吸収する構成**（LLM は構造化 JSON のみを吐き、描画は完全に自前コードで行う）
- **生成フェーズと再生フェーズの分離によるリプレイ可能性の確保**

これは評価パイプライン設計における「実行と評価の分離」と同型の構造であり、その転用可能性を確認する意図がある。

## 2. スコープ

### 2.1 対象範囲

- ローカル動画ファイルの読み込みと再生
- 映像フレームのサンプリングと LLM への送信
- タイムスタンプ付きコメントデータの生成
- 再生時刻に同期した弾幕描画

### 2.2 対象外（v0.1 時点）

| 項目 | 理由 |
|---|---|
| 音声・発話内容の解析 | v0.2 で対応予定（§7.1） |
| コメントデータの永続化・共有 | プロトタイプでは不要 |
| 動画のアップロード／サーバ保存 | プライバシー要件（§3.2）により明示的に非対応 |
| ユーザーによる手動コメント投稿 | 「群衆の代替」という目的から外れる |

---

## 3. 要件

### 3.1 機能要件

| ID | 要件 |
|---|---|
| FR-1 | ユーザーはローカルの動画ファイルを選択して再生できる |
| FR-2 | ユーザーの明示的な操作により、動画に対するコメント群を生成できる |
| FR-3 | 生成されたコメントは再生時刻に同期して画面右から左へ流れる |
| FR-4 | シーク操作を行っても、その時刻に対応するコメントが正しく表示される |
| FR-5 | 生成済みコメントを破棄し、再生成できる |

### 3.2 非機能要件

| ID | 要件 | 根拠 |
|---|---|---|
| NFR-1 | 動画ファイルは端末外に送出しない | 私的な映像を扱う前提のため。送出するのはフレーム画像のみ |
| NFR-2 | 同一の動画・同一のコメントデータで、再生結果が再現可能であること | デバッグ・チューニング時に生成結果を固定して比較する必要があるため |
| NFR-3 | コメント同士が視覚的に重ならないこと | 可読性。弾幕は密度が高いほど衝突が発生する |
| NFR-4 | LLM が想定外の出力を返しても、描画が破綻しないこと | LLM 出力は本質的に非決定的であるため |

## 4. アーキテクチャ

### 4.1 全体構成

```
[動画ファイル選択]
        ↓
[フレーム抽出フェーズ]  ── Canvas API で 6〜18 枚を等間隔サンプリング
        ↓                  各フレームを 400px 幅 / JPEG q=0.6 に縮小
[コメント生成フェーズ]  ── 5 枚バッチで Claude (vision) へ送信
        ↓                  タイムスタンプ付き JSON 配列を受領
[コメントデータ (JSON)]  ── [{t, text, size}, ...] を時刻順にソート
        ↓
[再生・描画フェーズ]    ── timeupdate イベントで発火判定
                           レーン管理付き弾幕レンダラで描画
```

### 4.2 フェーズ分離の設計判断

本アーキテクチャの中核は、**コメント生成と再生を明確に分離している**点にある。

**却下した案：リアルタイム生成方式**
再生しながら現在フレームを逐次 LLM に送り、返ってきたコメントをその場で流す方式。直感的だが以下の理由で採用しなかった。

- **レイテンシによる同期ズレ**: API 応答に数秒かかるため、コメントが反応対象のシーンより後に表示される。弾幕の面白さは「その瞬間への反応」であり、ズレると価値が消失する
- **シーク不能**: 巻き戻し・早送りに対して生成が追随できない
- **再現性の欠如**: 再生のたびに異なるコメントが出るため、プロンプト調整の効果を比較できない（NFR-2 違反）

**採用した案：事前一括生成方式**
生成をひとつのバッチ処理として完結させ、成果物としてタイムスタンプ付き JSON を得る。再生フェーズはその JSON を読むだけの決定的な処理になる。

この分離により、
- 同じコメントデータで何度でも再生できる
- シークが自然に動作する（時刻から該当コメントを引くだけ）
- プロンプトを変更した際、同一動画に対する出力差分を直接比較できる

**トレードオフ**: 動画を選んでから視聴可能になるまでに待ち時間（解析時間）が発生する。「動画を開いた瞬間に流れ始める」体験は犠牲になっている。ただし本用途では手元の動画を意図的に鑑賞する場面が主であり、初回の待機は許容可能と判断した。

### 4.3 LLM 出力の扱い

LLM には **HTML や描画命令を一切生成させない**。出力は以下のスキーマの JSON 配列のみに限定する。

```json
[
  { "t": 12.5, "text": "草", "size": "normal" },
  { "t": 13.1, "text": "ファッ!?", "size": "big" }
]
```

受領後、アプリケーション側で以下のバリデーションを行う。

- `t` が number であること（負値は 0 にクランプ）
- `text` が長さ 1 以上の string であること
- `text` は 40 文字で切り詰め
- `size` は `"big"` 以外をすべて `"normal"` に正規化
- 上記を満たさない要素は破棄

さらに、応答が JSON 以外の前置きを含む場合に備え、配列部分を抽出してからパースするフォールバックを持つ。

**設計意図**: LLM が壊れた出力を返しても、破棄されるコメントが数件増えるだけで描画は正常に継続する（NFR-4）。生成の非決定性を、スキーマ境界で決定的な領域へ変換している。

## 5. 詳細仕様

### 5.1 フレーム抽出

| パラメータ | 値 | 根拠 |
|---|---|---|
| サンプリング枚数 | 6〜18 枚（動画長に応じ自動決定） | 短い動画で過剰に、長い動画で過少にならないよう調整 |
| 送信解像度 | 幅 400px | シーンの識別に十分な最小サイズ。トークン量と精度の均衡点 |
| 画質 | JPEG quality 0.6 | 同上 |
| バッチサイズ | 5 枚／リクエスト | API コール数を抑制しつつ、1 リクエストの入力量を許容範囲に収める |

抽出は `video` 要素のシークと `canvas.drawImage()` によりクライアント側で完結する。動画本体はネットワークに出ない（NFR-1）。

### 5.2 コメント生成プロンプト

プロンプトの設計要件は以下の通り。

| 制約 | 内容 | 意図 |
|---|---|---|
| 密度 | 各フレームにつき 4〜7 件 | 弾幕として成立する最低密度の確保 |
| 時刻分散 | フレーム時刻の ±(サンプリング間隔/2) の範囲に散らす | 全コメントが同一時刻に集中すると「弾幕」ではなく「一斉表示」になる |
| 人格の混成 | 同意・ツッコミ・ボケ・逆張りを混ぜる | **最重要**。単一人格で生成すると論調が揃い、群衆に見えない |
| 具体性 | 画面に映っている内容に反応すること（汎用コメント禁止） | 「草」だけが並ぶと映像との関連が消える |
| 強調 | 盛り上がる瞬間は `size: "big"`、全体の約 1 割 | 平坦な弾幕は起伏を持たない |
| 冒頭固定 | t=0.5 のコメントは定型の挨拶で固定 | 文化的な様式の再現。開始時に必ず反応がある状態を作る |
| 文体 | 該当コミュニティの語彙・語尾を指定 | 弾幕の同一性はほぼ文体で決まる |

**設計判断（人格の混成）**: 初期案では「面白いコメントを N 件生成せよ」とのみ指示していたが、出力は論調の揃った一人の発話の羅列になり、群衆として認識されなかった。弾幕の本質は個々のコメントの質ではなく **意見の分布** にあると判断し、明示的に複数の反応類型を混ぜる指示に変更した。

### 5.3 弾幕レンダリング

**レーン管理による衝突回避**

画面を垂直方向に 11 レーンへ分割し、各レーンについて「次に空く時刻」を保持する。

```
lanes[i] = 現在時刻 + (コメント幅 / 総移動距離) × 流下時間 + マージン
```

新規コメントは `lanes[i] < 現在時刻` を満たす最初のレーンへ配置する。これは「前のコメントの末尾が画面右端を通過し切るまで、そのレーンを占有する」という条件に相当し、追突を構造的に排除する（NFR-3）。空きレーンが存在しない場合はランダムなレーンへフォールバックする（重なりを許容してでも表示する方を優先）。

**描画パラメータ**

| パラメータ | 値 |
|---|---|
| レーン数 | 11 |
| 流下時間 | 4.5〜6.5 秒（コメントごとにランダム） |
| 発火判定 | `timeupdate` イベント、`t - 1.0 < c.t <= t` の窓 |
| アニメーション | CSS transition による `translateX` |

流下時間をランダム化しているのは、一定にすると全コメントが等速で整列し、機械的な印象になるためである。

`translateX` の CSS transition を用いているのは、コンポジタスレッドで処理されレイアウトを発生させないため。`left` のアニメーションでは、コメント数が増えた際に再レイアウトが多発し描画が乱れる。

**シーク時の整合性**

`seeking` イベントで、表示済みフラグの集合をシーク先時刻より前のものだけに絞り込み、描画中の DOM 要素をすべて破棄する。これにより、巻き戻し後は該当区間のコメントが再度発火する（FR-4）。

## 6. 既知の制約

| 制約 | 影響 | 対応方針 |
|---|---|---|
| 音声・発話を解析していない | トーク主体の動画ではコメントが映像の見た目にしか反応せず、内容が薄くなる | §7.1 |
| ストリーミング動画等で `duration` が `Infinity` を返す場合がある | フレーム抽出の分割計算が破綻する | メタデータ取得完了までの待機処理と回避策を実装済み、検証中 |
| コメントの妥当性を機械的に評価できていない | プロンプト調整の効果測定が主観に依存 | §7.2 |
| API コール数が動画長に比例 | 長尺動画でコスト増 | バッチサイズの調整余地あり |

## 7. 今後の展開

### 7.1 音声情報の統合（v0.2）

音声を文字起こしし、フレーム画像と発話テキストの両方をプロンプトに含める。これにより「発言内容そのものへの反応」が生成可能になり、トーク動画での反応の薄さが解消される見込み。処理は既存の 2 フェーズ構成の生成側に追加するだけで、再生側の変更を要さない。フェーズ分離の設計が拡張コストを局所化している例と言える。

### 7.2 生成品質の評価軸の導入

現状、プロンプト変更の良否は目視判断に依存している。以下の定量指標を導入し、生成結果を比較可能にすることを検討している。

- 時刻分布の均一性（コメントの時間的な偏り）
- 語彙の重複率（同一表現の反復度合い）
- 映像内容との関連度（フレーム記述との語彙一致）

NFR-2 により同一動画・同一プロンプトでの再現が可能なため、A/B 比較の基盤は既に整っている。

## 8. 用語

| 用語 | 定義 |
|---|---|
| 弾幕（danmaku） | 動画再生画面上を横方向に流れるコメント表示形式 |
| レーン | 弾幕を配置する画面上の水平帯。衝突回避の単位 |
| 生成フェーズ | 動画からコメントデータを作る処理段階 |
| 再生フェーズ | 生成済みコメントデータを動画に同期表示する処理段階 |
